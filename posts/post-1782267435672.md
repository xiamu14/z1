## Loop Engineering 的核心：建立可验证的工程基础

Loop Engineering 是一种让 AI Agent 持续执行任务、检查结果并根据反馈继续修改的工作方式。它本质上是一个闭环控制系统：先设定目标，再执行任务、读取反馈、记录状态，并决定继续还是停止。

一个基本的 AI 开发循环包含五个部分：

1. **目标**：明确要完成什么，以及完成条件。
2. **执行**：由 Agent 编写代码、修改文件或调用工具。
3. **验证**：检查本轮结果是否满足完成条件。
4. **记忆**：记录已经完成的工作、验证结果和下一步任务。
5. **控制**：根据验证结果决定继续、停止或交给人工处理。

循环本身并不复杂。真正影响结果质量的，是目标和验证标准是否清楚。

## 先定义“什么算完成”

如果任务是“重写用户模块”，完成条件只有“项目能运行”，Agent 可能在通过基础检查的同时引入业务错误。例如，字段单位可能发生变化，边界条件可能被删除，并发保护也可能失效。

因此，开始执行前需要把目标写成可以检查的条件，例如：

- 指定功能行为保持不变；
- 类型检查无错误；
- 相关测试全部通过；
- 接口契约没有变化；
- 页面在不同尺寸和主题下显示正确；
- 不允许修改任务范围之外的文件。

执行者和验证者也应尽量分离。负责修改代码的 Agent 不应只依据自己的总结判断任务已经完成。验证结果需要附带证据，例如运行过哪些命令、检查了哪些页面、发现了什么结果。

## 让验证比改动更细

AI 开发循环需要对齐三种颗粒度：

- **任务颗粒度**：每轮允许修改多大范围；
- **验证颗粒度**：问题可以被定位到多具体；
- **记忆颗粒度**：执行过程被记录到多详细。

一轮改动越大，验证就越容易遗漏问题。更稳妥的方式是把大任务拆成边界明确的小任务，并为每个任务设置更细的验收条件。例如，与其一次重写整个模块，不如按函数、接口或用户场景逐步修改和验证。

记忆也需要适当的颗粒度。只记录“用户模块已完成”缺少恢复任务所需的信息；记录所有细节又会产生噪声。较实用的格式是按事件追加记录：做了什么、结果如何、证据是什么、下一步是什么。

## 为不同问题配置不同验证方式

没有一种检查工具能发现所有问题。验证应按成本从低到高分层执行：

1. **类型和静态约束**：发现字段、参数和返回值错误；
2. **代码关系检查**：确认调用方、依赖和变更影响范围；
3. **测试与契约检查**：验证业务规则和接口行为；
4. **运行时检查**：观察真实请求、并发和异常处理；
5. **视觉检查**：通过浏览器渲染和截图对比发现布局问题；
6. **模型或人工审查**：处理无法由确定性工具判断的语义、取舍和体验问题。

能由类型、约束函数或测试稳定判断的问题，应优先交给这些确定性工具。它们执行快、成本低，也能为 Agent 提供具体的修复信息。涉及审美、产品取舍或不可逆决策的问题，则需要保留人工判断。

强类型可以提高静态验证能力，但不能替代运行时测试和视觉检查。类型系统可以确认值的结构是否合法，却无法确认真实接口一定按预期返回，也无法判断页面是否出现文字截断或颜色对比问题。

## 限制 Agent 的操作范围

每轮任务开始前，应明确声明 Agent 可以读取的目录、修改的文件和运行的命令。未声明的操作默认不允许执行。

删除数据、修改生产环境、发送外部消息等不可逆操作，应在执行前暂停并请求人工确认。任务完成后，中间状态需要归档或清理，避免旧上下文影响下一轮判断。

这种设计的目标不是让 Agent 拥有尽可能多的工具，而是让它在完成当前任务所需的最小范围内工作。

## 持续校准，而不是只看一次结果

长期运行的系统还需要校准机制。每次判断应记录预期结果，并在实际结果出现后回填。例如，系统预测一次改动会提升性能，部署后就需要用真实数据核对预测。

从历史任务中总结出的新规则，不应直接加入正式流程。可以先在隔离环境中验证，并使用没有参与规则生成的新任务进行测试。验证通过后再启用，同时保留旧版本以便回退。

## 自动化不能替代可理解性

当 Agent 的产出速度超过团队理解代码的速度时，会形成理解缺口：系统可以运行，但维护者无法解释它为什么这样实现，也难以判断下一次修改的影响。

因此，AI 开发系统除了交付代码，还应保留可复盘的记录：

- 为什么进行这次修改；
- 使用了哪些完成条件；
- 运行了哪些验证；
- 哪些判断由工具完成，哪些由人完成；
- 失败时如何恢复。

Loop Engineering 降低了代码执行和反复修改的成本，但没有消除目标定义、任务拆分、质量判断和风险控制。可靠的 AI 开发流程，需要把这些要求转化为明确的约束、分层验证、持久记录和人工审查节点。
